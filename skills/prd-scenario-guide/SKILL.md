# 第二轮 · 场景交互导读

交付一份能在本地直接打开的单页 HTML。读者先能说出“同一个人为什么走到不同页面”，点进场景后能演示“我看到什么，能做什么，做了会怎样”。第一轮导读如已有，可辅助定位范围，直接从 PRD 开始也可以。

## 先定场景，再画页面

- 沿用用户指定的端、入口和业务范围。提取会改变可见页面、可做动作或操作结果的条件。仅在确实改变体验时，才按角色、时间、权限、首次或再次进入拆场景。同状态下查效果与申请退出可以是两个目标；避免枚举所有条件的组合。
- 以“谁，在什么情况下，想做什么”为场景标题。每个场景先写一行可观察结果。按真实生命周期组织阶段，同一阶段的不同选择并列；没有先后关系时按用户目标分组。期数和状态机只在有依据时使用。
- 读取对应 PRD 段落和现有代码，沿真实入口追到页面、组件、路由和响应消费位置。无 UI 稿时，用已有产品的页面骨架和交互习惯搭可操作示意。记录仓库、版本与相对路径。若代码已含本次实现且任务要求模拟开发前，取功能开发前基线。代码不可读时注明缺口，只为有依据的部分落图。
- PRD 说明业务要求，代码说明已存在的能力。已核实的接口和字段给出消费位置；缺合同时只写“前端需要知道什么”，点明谁确认。相似组件、截图、示例数据和后来的实现均不能单独证明新规则。原文冲突时两种口径就地可见，问题交给能决定它的人。

## 把场景做成一页 HTML

沿用「全域营销 · 商户分镜」的[第二轮桌面首屏](references/quanyu-desktop.png)。内联 [assets/guide.css](assets/guide.css)，使用 `body.guide > main.guide__page`。深紫底承载导读，金色标场景条件，米白画面呈现用户实际看到的界面。已选定此基准时直接沿用。场景名称、数量、端和业务角色随材料变化。

1. **首屏先看场景全貌。** 简短标题后直接呈现 `guide-map`。每个可点击的 `guide-case` 依次放触发条件（`guide-phase`）、代表性页面局部（`guide-screen`）与一句结果（`guide-case__result`）。有足够空间时横排同层场景。条件多时按用户目标或阶段分组。单场景走读、字段说明和大图排在全貌之后。
2. **进入后先回答问题，再看画面。** 保留返回入口。标题下用一句话说清商户或当前角色做完后去哪、何时能看到结果；随后用 `guide-strip` 内的 `guide-take` 演示“页面状态 → 可做操作 → 操作结果”。连续步骤用有序列表，时间跳转或角色交接写在对应画面上；同一判断的不同结果用无序列表并排，各自标出条件，参照[超时回查的并列分镜](references/quanyu-branches.png)。示意屏里的真实操作可演示，导读中模拟时间或切换条件的控件需与业务操作区分。未知去向就近标待确认。
3. **异常与技术判断按需查。** 把“提交失败怎么办”这类入口贴在发起操作的分镜旁，点击能到对应分支。场景下方用初始收起的 `details.guide-tools` 承载页面状态图、决策表和联调依据。状态图用已核实的触发条件连接页面；决策表按“条件／前端判断／用户看到什么与去向／口径及待确认方”对照。图和表共用分支标识，从表中可定位图中路径。大图可拖动、缩放和适应窗口。信息量少时按实际判断精简。影响落点的缺口在首层可见，证据和字段可展开。
4. **离线留存与核对。** CSS、脚本及图形内嵌；使用 Mermaid 时预渲染或内嵌运行时。每个场景可直达、可返回原入口。默认验证桌面，在浏览器逐一走通首页、分镜、异常分支、技术依据、返回和键盘操作。用户要求窄屏时再检查纵向阅读。提供实际 HTML 链接并区分本地导读演示、PRD/代码依据与待联调项。验收用例按用户要求另行展开。
