# 从零读懂需求

写给第一次接触这项业务的人。读完后，他应能用自己的话讲清楚谁因为这项需求获得什么结果、什么条件会改变结果，以及在哪里能感知这些变化。

使用用户已经提供的材料。正文、表格、批注、补充说明各自能证明什么就用什么。有链接且可访问时直接读取；只有部分内容时说明依据范围。若完全读不到需求，再请用户提供可读内容。无需用户先填写模板或给出代码仓库。

## 第一轮只交付三部分

1. **一句话业务。** 用参与者、诉求和业务结果说明这件事。若原文只说明规则变更，就说清该规则改变了谁的什么结果；背景或动机缺失时避免自行补写。
2. **关键条件和分支图。** 跨角色需求画出交接，状态型需求画出状态和触发事件，规则型需求直接从条件分到结果。用业务用语标注关键条件，区分用户可选动作、系统自动变化、延迟生效和重开等回路。只呈现原文支持的关系。画每条箭头前问：“即使前一步没有发生，后一步也可能发生吗？”如果可以，检查两者是否应从共同前提分别展开。阅读页面或章节的顺序不能证明因果。
3. **业务变化 → 用户可见的页面行为。** 点选图中任一变化后，展示对应的端或页面、观察者，以及此人看到的变化或能做的事。后台操作者和另一端的观察者可以是不同的人。说明前后差异，必要时指出后台操作如何改变另一端。页面名称不明时用原文已有的业务场景定位；纯后台变化可写“此时无直接可见变化”（仅在原文能确定时），或“是否对用户可见待确认”。

## 交付可留存的 HTML

默认实际写出一份能直接用浏览器打开的独立 HTML；用户明确指定其他格式时遵从其要求。将文件放在用户指定位置，或当前工作区内与该需求对应的持久目录。优先使用原生 HTML/CSS 和页内锚点，图及其交互离线可用，原文链接可按需联网访问。

**不点击，读懂业务。** 桌面首屏能顺着主线找到各分支的去向。窄屏先给可读的一句话和主线、分叉摘要，再纵向展开完整路径。按需求选择流程图、状态图或条件树，图上的文字保持可读。

- **决定和结果分开写。** 有多个可能结果时，节点写此刻谁在做什么，出线写触发条件，各自连接到实际结果。例如“商户阅读协议”可以通向“未同意 → 保持未开通”，也可以通向“同意并提交 → 到生效时点开通”。沿任一路径读，前面的动作都应与后面的条件相容。
- **把例外放进适用的规则组。** 先按会改变结果的条件分组，再将例外紧贴它修正的结果。若两条分支共用例外，在组内清晰写一次，并写全影响范围。例如两种站内收费结果旁共用“直销、续住免全站营销费”；站外种草另列。读者扫视结果时应同时看见这条限制。影响去向的未知就在该处分支标“待确认”。
- **连线表达因果。** 并行事件从共同前提分出，有回路时连回对应状态。跨角色时保留中间动作，例如“订单命中归因 → 平台计费 → 商户核账”。

**点击，看页面行为。** 初次打开只展示总图。每个业务变化可点选，也可通过节点直链打开同页详情，回答“哪个端、哪个页面、谁看到什么或能做什么”。桌面图默认静止；悬停或键盘聚焦时，只高亮当前节点直接相连的来路和去向。有方向性连线时可沿箭头流动，开启减少动态效果时用静态高亮。点击后的选中态与悬停态清楚区分，移开指针仍能对照图和详情。

手机详情紧跟所点节点展开，一次只展开一项；选项和答案之间不插入其他业务分支。切换节点时同步更新选中态与详情，收起后焦点回到原节点。

交付前先收起详情，按每条路径朗读“动作 → 条件 → 结果”，核对关键例外适用于哪几项。再在桌面和手机宽度逐个点选节点，检查对应页面、选中态和返回位置；手机上还要点一次中段分支，确认下一块内容就是它的详情。验证节点直链可打开对应内容。在回复里提供实际 HTML 文件链接。

## 把不确定性留在它发生的位置

影响主流程、分支条件或页面去向的缺口，就近标“待确认”，写清要决定什么；原文两处冲突时简列两种口径并指向出处。示意图只能佐证页面形态，不能单凭截图确定权限、默认值或业务规则。原文有可定位的章节或链接时，在对应疑点或产出末尾保留简短来源。

交付前核对：图中每条路径有依据，读者能从图中找到对应页面行为，原文未定的结果仍能看出是未知。具体功能拆解、控件细节、技术实现和验收用例留到第二轮，本轮到这里结束。
